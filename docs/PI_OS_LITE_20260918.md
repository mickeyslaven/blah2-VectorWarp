# Pi 4: fresh Raspberry Pi OS Lite installation

> **Maintained status:** This is the migration and measurement history for the
> Bookworm Lite Pi 4 baseline. Current deployment and AUTO guidance is in the
> [Pi 4 guide](PI4_GUIDE.md). The Pi 5 remains future work, and the prior
> Trixie package route is deprecated for new Pi installations. A supervised
> 40-minute soak with spike diagnostics is authorized; this historical record
> does not claim that it has completed successfully.

Status: the fresh OS is now the permanent default and has passed a normal
reboot. Recorded-IQ performance is measured; live RSPduo acceptance remains
incomplete.

This is a fresh 64-bit Raspberry Pi OS Lite Bookworm installation from 15
September 2026. It includes its own matching firmware, kernel, initramfs,
device trees, and kernel modules. It is not Fedora and does not reuse the OWL
operating system or its Docker services.

The staged base uses about 1.6 GiB of filesystem space and used 186 MiB of RAM

## Remote access and recovery

Access continues through the Pi Zero. The existing SSH configuration uses
`owl-pi4.local`, so the new system retains Avahi for that name. During migration,
the explicit address avoids reliance on the name cache:

```sh
ssh -F /Users/michaelslaven/Projects/owlos/work/ssh-config \
  -o HostName=192.168.1.211 owl-pi4-via-adsb
```

Existing SSH host keys, the `node` account's authorized keys, and Wi-Fi settings
were migrated within the Pi. Credentials are absent from this repository and
the public evidence. The factory image's disabled NetworkManager Wi-Fi state
was explicitly enabled; Wi-Fi power saving is disabled for reliable access.

The completed trial boots used the Pi's one-shot `tryboot` mechanism. Before
permanent acceptance, a static PID1 shim forked an independent 180-second
recovery process before starting systemd. Firmware started the watchdog with a
120-second open timeout, and systemd took over with a 15-second runtime
watchdog. The trial root mounted the shared FAT read-only.

The second trial proved all of these observations over SSH: new p4 root, new
kernel, firmware-injected watchdog timeout, active runtime watchdog, and a live
recovery process. Leaving the trial unaccepted returned the Pi automatically to
the previous p3 root and kernel. No physical card change was required.

Permanent activation is complete. A normal reboot started p4 on
`6.12.109+rpt-rpi-v8` without the trial init guard, with the hardware watchdog,
SSH, NetworkManager, SDRplay, Avahi, and the native API active; the browser UI
returned HTTP 200. Stable `config.txt` and `cmdline.txt` contain no recovery
guard. The old boot configuration is retained as
`/boot/firmware/config-owl-recovery.txt`. The previous root is mounted read-only
at `/mnt/vectorwarp-previous`; migration metadata is retained at
`/var/lib/vectorwarp/os-migration`. `tryboot` uses `cmdline-trial.txt` and its
separate 180-second guard only for future recovery trials.

The recovery process deliberately avoids a potentially blocking sync. Any
trial benchmark results must be explicitly flushed before the deadline. The
initial quick-run output was captured over SSH, but some files were not flushed
before recovery; those partial map files are not regression references.

## Current CPU result and acceptance limits

The current CPU candidate adds measured FFT plans, two clutter worker slots,
a preallocated paired RSPduo CPI queue, and reusable IQ buffers. The CPI timer
now includes direct IQ conversion; the earlier timer omitted roughly 40–65 ms
of allocation/conversion work per frame. The Pi runs at its stock 1.8 GHz with
the performance governor, without overclocking.

A fresh 60-second live run used both RSPduo channels at 2 MS/s, 551 MHz,
500 ms CPIs, 410 clutter taps, 411 delay bins, and 301 Doppler bins. Detection
and tracking were enabled. All 122 observed CPIs reported CPU ambiguity and
CPU clutter execution, with no GPU filtering. Including startup, mean time was
421.052 ms, p95 445.59 ms, p99 491.22 ms, and maximum 522.84 ms. Two CPIs
exceeded 500 ms. No samples were dropped, there were no capture faults, and
the stopped capture had no complete CPI backlog. The maximum sampled
temperature was 42.8 C, with no throttling.

That run used `/opt/vectorwarp/queue-reuse-full/bin/blah2`, SHA-256
`ae351a33552abf6e878acae5f8b822c831add369264aa003971a024afda62eed`.
Its evidence is on the Pi at
`/var/tmp/vectorwarp-soaks/cpu-only-60-20260918T2213Z/`. The candidate passed
26 application CTests, five benchmark CTests, and 18 full processor replay
cases. Recorded complex-map comparisons against the frozen oracle had RMS
relative error `4.416968e-11` and peak relative error `6.004779e-10`.

No 40-minute soak has passed. The first attempt stopped on a callback pairing
fault. The second lost one full CPI per channel after about 14 minutes. After
the reusable-buffer change, the third reached about 35 minutes 53 seconds but
the harness rejected its 4097th status message; it lacks a final capture
report and cannot certify sample retention through shutdown. That third run
averaged 452.831 ms over 4297 CPIs, with 26 CPIs at or above 500 ms. The harness
status capacity and repeated full-history validation have since been fixed
and regression-tested. Their effect on live timing has not been measured.

At the time of this historical entry, long soaks were paused while short CPU,
general GPU, and PR-style mixed-FIR comparisons completed. A separate
supervised 40-minute soak with spike diagnostics is now authorized; no result
is recorded here. The mixed FIR overlay is experimental benchmark code; it is
not installed as the production processor.

## Short CPU, GPU, and mixed comparison with tracking enabled

The subsequent three-way comparison kept detection and tracking enabled,
with the same two-channel 2 MS/s, 500 ms, 410-tap workload. The recorded test
used the same 40 IQ frames in each mode and excluded the first eight from its
steady statistics. The mixed mode offloaded 499,895 of 1,000,000 final FIR
samples to V3D, retaining CPU correlation, FP64 solving, and ambiguity work.
The general GPU mode is a different path; its small solve also remains on CPU.

| Mode | Recorded steady mean / p95 (ms) | Short live mean (ms), including startup | Live outcome |
| --- | --- | --- | --- |
| CPU | 402.157 / 405.596 | 419.707 | 30 seconds, 62 CPIs, zero loss or faults |
| General GPU | 936.710 / 937.253 | No qualified sustained result | Stopped after four startup CPIs; 3,000,000 samples lost per channel |
| Mixed 50% FIR prototype | 397.255 / 401.112 | 407.172 | 30 seconds, 62 CPIs, zero loss or faults |

CPU and mixed live runs used the same overlay binary. Each had one startup
CPI above 500 ms; their all-frame maxima were 507.82 and 523.97 ms. Excluding
the first two frames, their live means were 418.468 and 405.185 ms, and maxima
were 446.17 and 444.77 ms. Every mixed CPI logged actual V3D FIR execution;
its generic acceleration telemetry remains CPU because ambiguity is on CPU.

The mixed recorded output passed the existing complex-map accuracy gate:
RMS relative error `3.91e-6`, peak `4.30e-5`, both below `1e-4`. Detection and
tracking JSONL matched the CPU control byte-for-byte. General GPU output also
passed, with peak error `9.97e-5`, close to the same limit; both GPU stages
reported accepted Vulkan output without CPU fallback on all 32 steady frames.
Its unsuccessful live attempt averaged 1349.403 ms across four startup frames,
which is not a sustained-performance measurement.

These short results support a modest mixed-mode improvement on this workload,
not long-run qualification. The mixed backend currently executes inside an
isolated benchmark application rather than VectorWarp's production GPU worker.
No further long soak was started.

## Earlier runtime measurements

The new installation uses native SDRplay API 3.15 and native VectorWarp
processor/API/UI services. The private Node runtime is the repository-pinned
24.21.0 ARM64 release, verified against its pinned checksum. Numerical libraries
were copied from the previously tested build environment so the first OS
comparison uses the same processor and FFTW/BLAS implementation.

The first unchanged-processor check used the same recorded 2 MS/s input and
500 ms profile: 40 frames, first 8 excluded from steady statistics, 410 clutter
taps, 411 range bins, and 301 Doppler bins. Its preliminary steady mean was
550.235 ms, versus the previous campaign's 564.127 ms. The recovery deadline
discarded some unflushed artifacts, so this is not a retained regression result
or a repeated paired comparison. It does not meet the 400 ms target.

After permanent activation, the retained frozen quick check measured a steady
mean of 547.052 ms, p95 552.653 ms, and maximum 555.969 ms. The paired campaign
then ran three 40-frame CPU repetitions per revision, again retaining 32 steady
frames each. Frozen steady means were 543.544, 540.732, and 539.383 ms; the
combined correlation-and-FIR candidate measured 455.333, 457.637, and 454.277
ms. The pooled steady means are 541.220 ms frozen and 455.749 ms candidate.
Candidate p95 values were 458.478, 474.663, and 460.840 ms; maxima were
459.320, 493.001, and 478.078 ms. Every candidate complex-map comparison and
semantic JSON comparison was exact for all 40 frames of every paired repeat.

This is a recorded-IQ processing result, not a 400 ms or live-rate acceptance.
A 60-second candidate RSPduo attempt stopped early after eight CPIs with
231,768 FIFO-dropped samples per channel. Its total CPI times were 539–621 ms
and clutter took 281–379 ms. The normal stop completed, but the run failed the
live acceptance condition. Subsequent measured-plan, capture, and buffer
changes are described above; this earlier candidate is preserved separately.

The combined correlation-and-blocked-FIR candidate has passed its Pi build
validation: all 25 application CTests and all five benchmark CTests passed.
The validated application SHA-256 is
`cc13d7cf6fbf0f31e0575884eb95453dd199f323151c8442083fbf977ebaf539` and
the benchmark SHA-256 is
`e700645c2c69757610951359d83e7b73c1e68b8c94058a34e40ab661e9b3db51`.
The repeat campaign above is the first performance measurement with that
candidate. Live-radio acceptance and any further processing changes remain
open. The initial port's frozen baseline and campaign evidence remain in
`PI_ARM_PORT_RESULTS_20260918.md`.

## OWL PR context

[blah2-arm PR #67](https://github.com/offworldlabs/blah2-arm/pull/67) remains
open. Its reported OWL result was 4,781 CPIs across 40 minutes, mean 408.263
ms, with no CPI at or above 500 ms and no observed drops. It combines measured
FFT plans, parallel correlation and ambiguity work, bulk/direct capture, and a
50% hybrid V3D FIR split; tracker processing was off. Its companion
[owl-os PR #57](https://github.com/offworldlabs/owl-os/pull/57) is closed and
unmerged.

That result is useful design context but is not an equal comparison with this
campaign: VectorWarp has tracking on, uses a different application path, and
its generic GPU path was slower in the earlier qualification. The paired CPU
numbers above are the applicable VectorWarp evidence.

Local migration scripts and the working ledger are under ignored
`build/pi-os/`. Protected backups and full migration evidence are on the previous
Pi root under `/var/tmp/vectorwarp-os-20260918/`.
